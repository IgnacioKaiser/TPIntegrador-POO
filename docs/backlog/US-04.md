# US-04: usuarios persistentes

## Que incorpora este hito

El servidor cuenta con un modulo C++ que guarda usuarios en SQLite. Una herramienta local, usuarios_admin, permite preparar esa base. El servidor RPC aun no consulta los usuarios: eso corresponde a US-03.

Campos: id, nombre unico, clave_hash, rol y habilitado. Roles: ADMINISTRADOR y OPERADOR. Los listados nunca contienen claves ni hashes.

## Instalacion

Windows: abrir MSYS2 UCRT64 e instalar:

```bash
pacman -S --needed mingw-w64-ucrt-x86_64-sqlite3 mingw-w64-ucrt-x86_64-libsodium
```

Despues volver a PowerShell. Se conserva g++ de C:/msys64/ucrt64/bin. Esa carpeta tambien debe estar en PATH al ejecutar para encontrar las DLL. No instalar paquetes MINGW64 o MSYS en lugar de los UCRT64.

Linux Ubuntu/Debian: instalar libsqlite3-dev y libsodium-dev con el gestor de paquetes. Las dependencias nuevas solo las requiere el modulo de usuarios y sus pruebas.

Desde la raiz del proyecto:

```powershell
mingw32-make -C server
mingw32-make -C server test
```

En Linux usar make en lugar de mingw32-make.

## Uso en Windows

Ejecutar siempre desde la raiz para usar data/db/usuarios.sqlite:

```powershell
.\server\build\usuarios_admin.exe inicializar
.\server\build\usuarios_admin.exe agregar
.\server\build\usuarios_admin.exe listar
```

inicializar pide nombre y clave (dos veces) del primer administrador. Solo admite una tabla vacia. Repetirlo da error y conserva todos los datos y claves.

agregar pide las credenciales de un administrador existente y despues nombre y clave del nuevo operador. El operador nace habilitado. listar tambien exige un administrador y muestra solo datos de identidad/rol/estado.

Las claves no se muestran mientras se escriben en una terminal y no se pasan en argumentos del comando. Los usuarios admiten letras ASCII, numeros, _ y -, de 1 a 64 caracteres; distinguen mayusculas. Las claves admiten de 8 a 256 bytes UTF-8: es un limite sencillo de esta implementacion, no un requisito textual de la consigna.

Para otra ubicacion agregar --db "ruta/al/archivo.sqlite". Si no existe la carpeta, se crea. No inicializar otra base por accidente desde una carpeta diferente; para usar esa misma ruta en otra ubicacion, indicar --db explicitamente.

Cerrar y volver a ejecutar listar permite comprobar que los usuarios persisten entre procesos. No hay que tener el servidor RPC abierto para usar esta herramienta.

## Como se organiza el codigo

- usuario.hpp: Rol y Usuario. Usamos un struct porque es una vista de datos simple sin comportamiento propio ni secretos. No necesitamos herencia para diferenciar roles.
- repositorio_usuarios.hpp/.cpp: contiene las operaciones de persistencia. El constructor abre la base y crea tabla/indice si faltan. El destructor cierra la conexion.
- inicializarAdministrador: inicia una transaccion, comprueba que no haya usuarios y crea el administrador. Si falla algo hace rollback, es decir, deshace esa inicializacion.
- agregarOperador: exige que exista un administrador e incorpora un usuario de rol OPERADOR. La autorizacion del operador humano se comprueba en la herramienta, no dentro del repositorio; en US-03 la comprobara la capa de servicios.
- buscar: devuelve optional<Usuario>; nullopt significa que el nombre no existe.
- listar: devuelve un vector<Usuario> sin credenciales.
- verificarClave: consulta internamente el hash y usa libsodium para verificar una clave. No comprueba el rol ni la habilitacion: esas son condiciones adicionales de acceso.
- insertar: operacion privada comun al alta inicial y al alta de operadores. Valida los datos y genera la cadena hash con libsodium.
- Sentencia: auxiliar privada que libera las consultas preparadas de SQLite en su destructor. Sus parametros se asignan con bind, sin concatenar la entrada del usuario en SQL.
- tools/usuarios_admin.cpp: consola de administracion local separada del main del servidor para evitar dos main en un ejecutable.

Se usan punteros proporcionados por la API C de SQLite, encapsulados en clases que los liberan. No se agrega new manual. Se impide copiar el repositorio y las sentencias porque no deben cerrar dos veces el mismo recurso.

## Decisiones y limites

SQLite satisface el requisito de base de datos sin configurar otro servidor. libsodium evita escribir criptografia propia. Su API almacena hash, salt y parametros en una cadena. Se usan limites de costo INTERACTIVE.

Un indice unico parcial impide dos administradores incluso si se intenta insertar directamente con SQL. La inicializacion garantiza el primero; la API no permite eliminarlo ni cambiar su rol. No se agrega CRUD general, restablecimiento de claves ni activacion/desactivacion remota: excederian este hito.

Se encapsulan los datos pero no se promete proteccion ante alguien con acceso directo de escritura al archivo SQLite. Los permisos de acceso a las funciones se comprueban en la aplicacion.

El archivo real y los auxiliares SQLite se ignoran en Git. Se comparten codigo, pruebas y documentacion; cada equipo inicializa su base y sus claves reales. Las claves que aparecen en pruebas son ficticias y se usan exclusivamente en bases temporales.

US-03 protegera las peticiones RPC. Por ahora ping y eco siguen como antes. Esta herramienta no reemplaza la CLI completa de control del robot exigida por el TPI; es un paso de preparacion de usuarios.

## Pruebas incluidas

make test-usuarios (o mingw32-make -C server test-usuarios desde la raiz) crea una base temporal unica. Verifica:

- No agregar operadores antes del administrador.
- Persistencia al cerrar y reabrir.
- Claves correctas, incorrectas y usuario inexistente.
- Nombre duplicado rechazado sin sobrescribir su clave.
- Reinicializacion rechazada sin cambiar datos.
- Restriccion de segundo administrador directamente en SQL.
- Nombre y clave invalidos rechazados.
- Administracion rechazada para un operador o clave incorrecta.
- Alta y listado administrativo sin mostrar secretos.
- Almacenamiento de hashes, no de claves originales.

La base real nunca se utiliza para estas pruebas. El ejecutor Python elimina las bases temporales al terminar.
