# US-03: validar cada peticion antes de ejecutar

## Que cambia para el usuario

El cliente pide usuario y clave. Con esos datos solicita ping o eco. El servidor comprueba cada peticion contra la tabla creada en US-04. Una clave incorrecta, un usuario inexistente o una cuenta deshabilitada no llegan a la operacion solicitada.

Los usuarios y claves creados en US-04 se conservan. No se incluye una base en este entregable y no hay que inicializarla de nuevo. Este hito no agrega movimientos ni la administracion remota de habilitaciones (US-05).

## Conceptos necesarios

Autenticacion significa comprobar quien hace una solicitud: usuario y clave. Autorizacion significa decidir si ese usuario tiene permiso para una accion. Ping, eco y consulta de estado aceptan cualquier usuario autenticado y habilitado. El acceso a conectar y desconectar el robot y a administrar operadores requiere el rol ADMINISTRADOR. Tener una clave correcta no concede automaticamente permisos de administrador.

Una sesion seria un mecanismo para recordar en el servidor que alguien se identifico antes. No agregamos sesiones ni tokens en esta etapa: la consigna pide verificar cada peticion mediante usuario y clave. El cliente conserva las credenciales en memoria mientras esta abierto, pero las manda de nuevo en cada solicitud. El servidor consulta de nuevo la base; no confia en un nombre que el cliente declare sin verificar.

El hash almacenado es una huella que permite comprobar la clave, no una clave que el servidor descifra. libsodium verifica esa huella. SQLite conserva identidad, hash, rol y estado. Son tareas diferentes y ambas se explican con mas detalle en US-04.md.

## Recorrido de una solicitud

1. El cliente obtiene las credenciales con input y getpass. getpass oculta la clave en una terminal normal.
2. ServiciosPrueba agrega credenciales al objeto MensajeRPC de ping/eco.
3. ClienteXmlRpc transmite el mensaje como antes. No imprime ni guarda la clave.
4. El adaptador C++ reconstruye el mensaje recibido.
5. ServicioProtegido llama a Autenticador antes de invocar el servicio.
6. Autenticador comprueba tipos, existencia, clave y habilitacion, consultando el repositorio SQLite.
7. Si rechaza, se construye la respuesta de error y se retorna inmediatamente. No se llama a la operacion.
8. Si acepta, ServicioProtegido retira las credenciales de una copia de los parametros, comprueba los permisos de la operacion y llama a ServicioRobot. La operacion recibe solo sus propios datos.

El cliente ayuda al usuario, pero la decision de permitir una peticion esta en el servidor. Por eso enviar una solicitud manual por XML-RPC tampoco permite evitar la comprobacion.

## Formato y respuestas

Se conservan los seis campos externos. Dentro de parametros se agrega:

```text
credenciales:
    usuario: nombre
    clave: clave ingresada
```

Para eco, texto es otro campo de parametros, al mismo nivel que credenciales. No se crea un septimo campo externo ni otro formato de mensaje. Esto aprovecha las estructuras anidadas que ValorRPC ya soporta.

- NO_AUTENTICADO: credenciales ausentes o usuario/clave incorrectos. El mismo mensaje para usuario inexistente y clave incorrecta evita informar si una cuenta existe.
- VALIDACION: estructura o tipos de las credenciales incorrectos, o parametros de operacion invalidos una vez autenticado.
- PERMISO_DENEGADO: clave correcta de una cuenta deshabilitada.
- ERROR_INTERNO: no se puede consultar la base. No se interpreta como clave incorrecta y no se ejecuta la operacion.
- OK: la operacion definida se completo; no significa que un robot se haya movido.

Los errores del formato externo XML-RPC siguen siendo Fault. Los metodos system.* de la biblioteca mantienen la consulta de metadatos; ninguna operacion de aplicacion se publica por fuera de ServicioProtegido.

## Archivos y funciones

- autenticador.hpp/.cpp: Autenticador recibe una referencia al repositorio. validar devuelve Usuario o lanza ErrorAutenticacion con codigo y mensaje. No imprime, no abre menus y no mueve el robot.
- servicio_protegido.hpp/.cpp: atender controla el orden autenticar-antes-de-ejecutar. Atrapa los errores de acceso y los convierte en respuestas normales. Un return temprano impide continuar ante un rechazo.
- servidor.hpp/.cpp: el servidor construye repositorio, autenticador, servicio y acceso protegido en ese orden. Las referencias no son duenas de los objetos: el servidor mantiene sus vidas utiles. El adaptador solo conoce ServicioProtegido.
- main.cpp: permite --db para elegir la misma base que usuarios_admin y --port para el puerto. El servidor exige exactamente un administrador habilitado al iniciar; si falta, explica que debe inicializarse.
- cliente.py: ServiciosPrueba recibe usuario/clave y los incluye en cada mensaje. ClienteXmlRpc conserva su responsabilidad de transporte y correlacion de respuesta.
- cli.py: solicita credenciales una vez por ejecucion mediante getpass. En modo comando devuelve codigo de salida distinto de cero si la operacion es rechazada. En el menu permite volver a intentar operaciones; para cambiar credenciales se cierra y reabre el cliente.
- Makefile: enlaza el servidor con los objetos de usuarios, SQLite y libsodium. Agrega test-autenticacion a test.

## Por que una clase de acceso protegido

Poner un if de contrasena en cada operacion es corto al principio, pero facil de olvidar al agregar una nueva. Un acceso comun permite verificar una sola vez por peticion y conservar las operaciones separadas de la autenticacion. No se agrega un framework ni una jerarquia de permisos.

ServicioRobot::atender es virtual para permitir sustituir el servicio por un espia en pruebas. ServicioProtegido utiliza esa interfaz común; no se agrega un contador artificial al servicio real.

El Usuario devuelto por Autenticador habilita los controles de permisos del servidor. ServicioProtegido verifica el rol de administrador antes de conectar o desconectar el robot y antes de administrar operadores; el cliente no puede enviar un rol propio para eludir esa comprobacion.

## Ejecucion en Windows desde la raiz

Compilar y probar, con las dependencias de US-04 instaladas:

```powershell
mingw32-make -C server
mingw32-make -C server test
```

Terminal 1:

```powershell
.\server\build\robot_server.exe
```

Terminal 2:

```powershell
python client/main.py ping
python client/main.py eco "Hola"
python client/main.py
```

Cada ejecucion pide usuario y clave. Usar las credenciales propias de la base de US-04; las claves de los tests solo existen en sus bases temporales.

Si el archivo esta en otro lugar, configurar la misma ruta en ambos programas, por ejemplo:

```powershell
.\server\build\robot_server.exe --db "data/db/usuarios.sqlite"
```

Cerrar el cliente y repetir con clave incorrecta debe dar NO_AUTENTICADO. Volver a ejecutar con un usuario inexistente debe producir el mismo rechazo. Un operador habilitado debe poder usar ping y eco. Cerrar el servidor con Ctrl+C.

## Pruebas y alcance verificado

Se mantienen las 15 comprobaciones del dominio/servicio original y las 10 pruebas Python, actualizadas para comprobar que los servicios del cliente incluyen credenciales. Se conservan las pruebas de usuarios de US-04 y se agrega una prueba C++ del acceso protegido:

- Clave correcta: invoca exactamente una vez al servicio.
- Clave incorrecta, usuario inexistente, credenciales ausentes o mal tipadas: respuesta de error y ninguna invocacion.
- Cuenta deshabilitada: rechazo sin ejecucion.
- Cambio de habilitacion entre dos peticiones: se refleja en la siguiente, con las mismas credenciales.
- Fallo de consulta de base de datos: ERROR_INTERNO sin invocar al servicio.
- El servicio no recibe las credenciales y las respuestas conservan el ID.

Las pruebas de integracion crean una base temporal con usuarios ficticios mediante usuarios_admin y arrancan el servidor con --db apuntando a ella. Comprueban las operaciones por red, rechazos y estado de cuenta. Se agregan dos pruebas a las 16 anteriores: total 18.

Cambiar la habilitacion directamente con SQLite se hace solo para preparar los escenarios de prueba; no implementa US-05. Las conexiones Python se cierran mediante closing antes de borrar los archivos temporales.

La prueba automatica de CLI sustituye solo la lectura oculta de clave para poder alimentar un subproceso en Windows y Linux. Se mantiene la comunicacion real con el servidor. La lectura oculta real se comprueba manualmente.

## Limites de esta etapa

El hash protege el almacenamiento de la clave, no cifra HTTP. La escucha sigue limitada a la computadora local (127.0.0.1). Una futura apertura a otras computadoras requiere tratar el transporte de credenciales; este hito no agrega TLS ni afirma que HTTP transporte las claves cifradas.

No hay gestion de sesiones ni recuperacion de claves. Las solicitudes autenticadas envian usuario y clave en cada llamada; HTTP sigue limitado a loopback y no cifra el transporte. Las respuestas y la salida del servidor no incluyen claves ni hashes. Los documentos y pruebas usan credenciales ficticias, no las del equipo.
