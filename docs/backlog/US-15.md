# US-15: recibir y almacenar archivos de tareas

Estado: Hitos A y B implementados y verificados en Windows en esta rama.
Fecha: 27/10/2026. Rama: us-15-16-24-tareas. Base del Hito B: 08b0f4e (Hito A).
Integracion a master y ejecucion de pruebas en Linux pendientes.

## Problema y solucion de este hito

Necesitamos conservar una tarea aunque el servidor se cierre. RepositorioTareas
guarda el contenido en un archivo dentro de la carpeta del propietario:

```text
directorio_configurado/
  2/
    pieza.gcode
  3/
    pieza.gcode
```

Dos usuarios pueden tener pieza.gcode. El mismo propietario no puede volver a
guardarla ni sobrescribirla cambiando mayusculas. El identificador logico es, por
ejemplo, `2:pieza.gcode`: no es una ruta que el cliente pueda elegir.

La consigna exige almacenar tareas G-Code; los criterios de US-15 piden un
directorio administrado y asociacion con el propietario. Los limites concretos de
nombres, extensiones, contenido y concurrencia son decisiones aceptadas del equipo.
La decision compartida y sus alternativas se explican en D11 de DECISIONES_DISENO.md.

## Clases y funciones

- `Tarea` es un struct: una clase simple de datos, con id, propietario_id y nombre.
  Representa lo necesario para listar, sin leer todos los contenidos en memoria.
- `RepositorioTareas(directorio)` prepara y resuelve la raiz configurada del almacen.
  La ruta es configuracion local del servidor, nunca un dato del usuario remoto.
- `guardar(usuario, nombre, contenido)` comprueba el Usuario recibido, normaliza y
  valida, escribe un temporal y publica el archivo terminado. Devuelve una Tarea.
- `listar(usuario)` se explica en US-16.md.
- `ErrorTarea` distingue VALIDACION, DUPLICADA, ACCESO_DENEGADO y ALMACENAMIENTO.
  Son errores del dominio; todavia no estan conectados a codigos RPC.

El parametro Usuario proviene de la capa autenticada al recibir la solicitud RPC.
El repositorio comprueba ID positivo, rol conocido y habilitado, pero no verifica
claves ni reemplaza Autenticador. ServicioProtegido verifica las credenciales antes
de llamar al repositorio. No recibe un ID de propietario como argumento
independiente. Un administrador tambien guarda en su propia carpeta.

## Reglas de nombres y contenido

Nombre de hasta 64 caracteres, extension incluida; nombre base no vacio con letras
ASCII, numeros, guion o guion bajo y extension .gcode o .nc. Se normaliza a minusculas.
Se rechazan rutas, separadores, otros puntos y nombres reservados de Windows como
CON, NUL, PRN, AUX, COM1-COM9 y LPT1-LPT9. El resultado es el mismo en Windows y Linux.

Contenido de 1 byte a 1 MiB (1.048.576 bytes, contado antes de normalizar), UTF-8
valido y compatible con caracteres XML 1.0. Se rechazan NUL, controles no permitidos,
secuencias UTF-8 invalidas y archivos sin ordenes. Se quita el BOM inicial de UTF-8
y se normalizan CRLF y CR a LF. Se conservan comentarios, lineas vacias, mayusculas
y parametros; no se agrega ni se exige un salto final.

La revision no encontro archivos .gcode/.nc de ejemplo independientes en el repo.
Se revisaron `firmware/arduino/robotArm_v0.62sim/command.cpp`, el .ino y las ordenes
de Robot, documentacion y pruebas. El firmware convierte a mayusculas y elimina
espacios; por eso el almacen admite tanto `G1 X10 Y20` como `g01x10y20`, `G 90`,
decimales con signo y los parametros X/Y/Z/E/F/S sin intentar interpretarlos.

El control de formato solo reconoce un prefijo G o M seguido de digitos, con espacios
o tabulaciones opcionales. Tambien permite numero de linea N seguido de digitos,
comentarios con `;` o parentesis (incluso entre lineas), y lineas separadoras `%`.
Debe haber al menos una orden. Los comentarios entre parentesis deben cerrarse.
Las otras lineas de texto se rechazan; no se soportan todos los dialectos de G-Code,
macros ni lineas modales que comiencen solo con X/F/T u otras letras.

Comentarios, N y % se aceptan como formato de archivo: el firmware actual no los
interpreta necesariamente si se envian crudos. La futura ejecucion tendra que tratar
esos formatos. No se validan checksums, argumentos, codigos disponibles, coordenadas,
velocidades ni trayectorias. Incluso `G999 X999999 F-50` puede almacenarse: esto
demuestra que almacenar no ejecuta ordenes ni certifica que una tarea sea ejecutable.

## Escritura y fallos

Se escribe en `.nombre.gcode.tmp` dentro de la misma carpeta. Se comprueba el cierre
y se renombra al nombre definitivo. El listado ignora temporales, incluidos restos
de un cierre inesperado. Una nueva subida del mismo nombre puede reutilizar ese
temporal regular; no reutiliza enlaces ni directorios. Los errores normales eliminan
solo el temporal creado por esa operacion, sin borrar tareas existentes.

No se siguen enlaces simbolicos en las carpetas de propietario ni en archivos de
tareas o temporales. Los archivos externos no deben ser manipulados manualmente
dentro de este directorio administrado. La raiz configurada se resuelve al construir.
Se supone un unico escritor con llamadas secuenciales, como el servidor actual.
No hay garantias para varios procesos/hilos escribiendo el mismo almacen ni una
garantia especial ante corte de energia. No se agrega infraestructura para esos casos.

## Como probar y que se verifico

Desde la raiz en Windows:

```powershell
mingw32-make -C server test-tareas
```

En Linux: `make -C server test-tareas` (pendiente de ejecucion en Linux).
`ejecutar_tareas.py` crea una carpeta con TemporaryDirectory, ejecuta test_tareas
y la elimina al terminar. Nunca usa data/trayectorias ni una base real.

En Windows nativo/MSYS2 UCRT64, g++ 15.2.0 y Python 3.14.0 pasaron 59 comprobaciones
del repositorio. Incluyen reapertura, contenido persistente, nombres repetidos,
aislamiento por propietario, texto UTF-8 con comentarios, formato del firmware,
limites de nombre y bytes, entradas invalidas y temporales no listados.
Un directorio en el lugar de un temporal impide guardar sin necesidad de mocks:
se detecta el obstaculo, no se publica una tarea parcial ni se elimina ese directorio.

Las pruebas de enlaces de archivo y directorio se omitieron porque Windows no
permitio crearlos. Su rechazo esta implementado pero no se presenta como verificado.
No se simularon disco lleno, corte de energia ni escritura simultanea. No se uso Arduino.
El resultado de la suite completa se registra en ESTADO_PROYECTO.md.

## Limites y siguiente paso

**La base de usuarios y las carpetas de tareas se deben conservar y respaldar juntas.**
Cambiar/reinicializar la base puede cambiar o reutilizar IDs y asociar tareas antiguas
a otras personas. No se agrego un mecanismo para reasignar propietarios ni migrar
esas instalaciones. Esta limitacion se explica tambien en la decision compartida D11.

Hito B ya conecta recepcion autenticada y cliente; no se agregan cambios en Robot,
borrado, descarga, edicion ni sobrescritura de tareas. Almacenar no ejecuta ordenes.

## Hito B: recepcion autenticada y verificacion real

`ServidorXmlRpc` construye el repositorio con la opcion `--tareas-dir` (por defecto
data/trayectorias). `ServicioProtegido` recibe esa referencia. En tarea.subir acepta
solo nombre/contenido y pasa el Usuario que acaba de autenticar. Devuelve identidad
de la tarea y confirmacion de almacenamiento. El contrato exacto esta en CONTRATO.md.

El propietario no depende del nombre del archivo ni de un parametro de la solicitud.
Un campo adicional propietario, usuario_id, rol o ruta produce VALIDACION. Los
errores de dominio se traducen a los codigos acordados: DUPLICADA se presenta como
ESTADO_INVALIDO; los fallos del almacen como ERROR_INTERNO, sin rutas ni contenido.
No se delegan estas operaciones a ServicioRobot. D12 explica el recorrido compartido.

Se ejecuto la suite completa `mingw32-make -C server test`: dominio, usuarios,
autenticacion, 59 comprobaciones del almacenamiento, 43 pruebas simuladas del
cliente y 32 de integracion real con C++ correctas en Windows nativo/MSYS2 UCRT64,
g++ 15.2.0 y Python 3.14.0. No se ejecuto Linux ni se uso Arduino.

La integracion prueba subida desde el proceso CLI Python con UTF-8/BOM/CRLF,
contenido normalizado en disco, tres propietarios con el mismo nombre de tarea,
reinicio del servidor y persistencia. Comprueba duplicados sin sobrescritura,
entradas invalidas, tamano excesivo enviado saltando el control local, intentos de
elegir propietario, ausencia de credenciales, claves incorrectas y cuenta deshabilitada
sin escrituras. Cuatro clientes concurrentes obtuvieron un OK y tres ESTADO_INVALIDO;
el contenido final coincide con el de la unica subida aceptada. Los logs de esa
prueba no contienen el marcador de contenido del archivo.

Un servicio espia en la prueba C++ confirma que subir/listar no llaman al servicio
del robot. Las bases y carpetas son temporales explicitas en todos los constructores
y procesos de prueba, incluido el segundo servidor del caso puerto ocupado.
Los enlaces simbolicos siguen omitidos en este entorno, como se indica arriba.
La prueba manual breve del bloque esta en US-24.md; no es necesario repetir todos
los casos automaticos para probar el uso normal.
