El cliente permite solicitar conexion, desconexion, estado, activacion y desactivacion
de motores y ayuda. Se pueden pedir desde la terminal o desde el menu interactivo.

## Como funciona y por que

1. La consola pide usuario y clave con el mecanismo existente (`getpass` no muestra
   la clave mientras se escribe). No se agregaron claves en argumentos ni archivos.
2. `ServiciosPrueba` construye el pedido y agrega las credenciales en cada solicitud.
   Conservamos el nombre de la clase para no romper los consumidores existentes.
3. `ClienteXmlRpc` llama al metodo remoto `robot.intercambiar`. XML-RPC es el
   mecanismo que transporta datos entre Python y C++; ya existia en el proyecto.
4. El servidor autentica cada pedido, comprueba permisos y responde. Solo un
   administrador puede conectar o desconectar; el cliente no decide esos permisos.
5. La consola muestra el codigo, el mensaje y todos los datos restantes del resultado.

Los seis metodos nuevos de `ServiciosPrueba` se llaman como las operaciones:
`conectar(puerto=None)`, `desconectar()`, `estado()`, `activar_motores()`,
`desactivar_motores()` y `ayuda()`. Solo conectar admite un dato adicional.
`None` es un valor local de Python: significa omitir el parametro, nunca enviar `nil`.
El puerto corresponde a la computadora del servidor, no a la del cliente.
El servidor usa COM3 en Windows o /dev/ttyACM0 en Linux si se omite.

`CliCliente.mostrar_datos` recorre los diccionarios internos con sangria (espacios)
para mostrar que datos pertenecen a posicion, motores u otro grupo. Los booleanos
se imprimen como `si` y `no`. Por ejemplo:

```text
[OK] Respuesta del servidor.
conectado: no
posicion:
  disponible: no
  mensaje: El robot esta desconectado; no se puede consultar la posicion.
actividad:
  motores:
    disponible: no
    mensaje: El estado de los motores requiere consultar el firmware.
```

La salida completa incluye tambien los otros grupos enviados por el servidor y el
ID del pedido. No se completan campos ausentes con ceros: `disponible: no` significa
que el dato es desconocido. `activo: no` con `disponible: si` significa un estado
inactivo conocido. Un error de estado puede traer datos parciales y tambien se muestran.

Para motores, se presenta la respuesta del firmware y se aclara que esa confirmacion
no verifica una accion fisica. Ante un fallo de comunicacion se informa que no se
puede confirmar la ejecucion; se conserva el transporte sin reintentos automaticos.
Reenviar una orden por perder su respuesta podria repetir una accion ya realizada.

Se reutilizan `argparse`, `getpass` y `unittest`, incluidos en Python. `argparse`
interpreta los comandos de terminal, `getpass` pide la clave y `unittest` ejecuta las
pruebas. No agregamos dependencias ni jerarquias de clases. Mostrar los datos
anidados con una funcion corta evita mantener una pantalla diferente por cada campo.

## Uso del cliente

Desde la raiz de `us-23-cliente`, con el servidor ya iniciado:

```powershell
python client/main.py ayuda
python client/main.py estado
python client/main.py conectar
python client/main.py conectar COM4
python client/main.py desconectar
python client/main.py activar_motores
python client/main.py desactivar_motores
python client/main.py
```

Cada ejecucion pide las credenciales. Sin comando abre el menu: las opciones 5 a 10
son las seis nuevas operaciones. En conectar, Enter omite el puerto. Se conservan
ping, eco y las opciones de usuarios existentes.
En Linux usar `python3`; por ejemplo `python3 client/main.py conectar /dev/ttyACM0`.
`python client/main.py --help` muestra la sintaxis sin pedir credenciales;
`ayuda` consulta al servidor y si requiere autenticacion.

`--url` y `--timeout` van antes del comando:

```powershell
python client/main.py --url http://127.0.0.1:8081/RPC2 --timeout 10 estado
```

El timeout existente por defecto sigue siendo 3 segundos; se puede ampliar para
verificar el puerto serie. ConState espera 2 segundos al abrirlo por el reinicio del
Arduino. Ampliar el timeout no agrega reintentos. Un comando retorna 0 si recibe OK,
o 1 si recibe un error. En el menu un rechazo se muestra y permite seguir eligiendo.

## Pruebas simuladas ejecutadas

Desde la raiz, en Windows o Linux (usar `python3` si corresponde):

```text
python -B -c "import sys,unittest; sys.path.insert(0,'client'); unittest.main(module=None, argv=['unittest','discover','-s','client/tests','-v'])"
```

`-B` evita crear archivos de cache. Resultado: **26 pruebas correctas en Windows,
Python 3.14.0**: 14 existentes y 12 nuevas en `client/tests/test_us23.py`.
Tambien se comprobo el formato del diff con `git diff --check`.

Las pruebas nuevas sustituyen la respuesta de red mediante `unittest.mock`:
un sustituto permite decidir que contestaria el servidor sin abrir una conexion.
Comprueban las seis solicitudes, puerto omitido o explicito, credenciales por pedido,
comandos de terminal, opciones del menu, rechazos y continuidad del menu,
posicion desconocida, valores reales incluidos ceros, datos parciales con error,
ayuda con saltos de linea y confirmacion de firmware. Simulan ademas un timeout
y comprueban que se hace un solo intento. Se verifica que la salida no incluya
la clave ficticia usada en las pruebas.

Estas pruebas automaticas no abren el puerto serie, no crean usuarios y no usan bases reales.
No demuestran que el servidor autentique correctamente ni que Arduino ejecute ordenes.
El agente no ejecuto Linux, el servidor C++ ni el controlador en esta etapa.

## Como verificar con el servidor real (preparacion y casos restantes)

Usar una copia separada de ConState en el commit indicado, o pedir al companero
que inicie ese servidor. Mantener esta copia en `us-23-cliente`; el servidor local
de esta rama aun no tiene las operaciones nuevas. No hace falta mezclar ramas.
Como ConState escucha en 127.0.0.1, ejecutar ambos procesos en la misma computadora.

En la raiz de la copia de ConState, Windows/PowerShell:

```powershell
mingw32-make -C server
$basePrueba = Join-Path ([System.IO.Path]::GetTempPath()) ("us23-" + [guid]::NewGuid().ToString("N") + ".sqlite")
.\server\build\usuarios_admin.exe inicializar --db $basePrueba
.\server\build\usuarios_admin.exe agregar --db $basePrueba
.\server\build\robot_server.exe --db $basePrueba --port 8081
```

Elegir cuentas y claves de prueba al solicitarlas la herramienta. Inicializar crea
el administrador en esa base temporal nueva; agregar crea un operador tras validar
al administrador. No usar la base habitual ni escribir claves en los comandos.
En Linux, los comandos equivalentes desde esa copia son:

```bash
make -C server
base_prueba="$(mktemp -d)/usuarios.sqlite"
./server/build/usuarios_admin inicializar --db "$base_prueba"
./server/build/usuarios_admin agregar --db "$base_prueba"
./server/build/robot_server --db "$base_prueba" --port 8081
```

Desde otra terminal, en la raiz de `us-23-cliente`, probar con `--url
http://127.0.0.1:8081/RPC2` antes de cada comando:

1. Como operador: ayuda y estado sin robot conectado. Esperar datos no disponibles;
   activar/desactivar motores debe responder ESTADO_INVALIDO.
2. Como operador: conectar y desconectar deben devolver PERMISO_DENEGADO.
   Con una clave incorrecta, esperar NO_AUTENTICADO.
3. Como administrador: conectar a `puerto-inexistente` debe devolver ERROR_CONEXION;
   desconectar debe aceptar que el robot ya este desconectado.
4. Con Arduino y el firmware simulador provisto, usar su puerto real, consultar estado
   y solicitar motores. Verificar las respuestas del firmware y sus indicadores de
   disponibilidad. El simulador no demuestra movimiento fisico.
5. Abrir el menu y repetir un rechazo seguido de otra consulta para verificar continuidad.

Registrar por separado entorno, commit del servidor, equipo usado y resultados reales.
Las pruebas de dominio, autenticacion e integracion de ConState se revisaron como
referencia de comportamiento; no se ejecutaron ni se modificaron desde esta rama.

## Pendientes

ConState no devuelve identidad ni permisos consultables. Conectar y desconectar
se identifican como administrativas, pero se muestran a todos. El servidor decide
y el cliente presenta PERMISO_DENEGADO. No se deduce el rol por el nombre ni se
pide al usuario que se declare administrador. Filtrar el menu requiere acordar una
respuesta autenticada con esa informacion. La decision se registra en D09 de
`docs/DECISIONES_DISENO.md`.

La US-23 sigue parcialmente implementada: falta ese filtrado, completar la verificacion real
y el consumo futuro de otros servicios cuando existan y se acuerde su alcance.
