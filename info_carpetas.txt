# Organización del proyecto integrador

## 1. Objetivo de esta organización

Este documento define la estructura de carpetas del trabajo integrador y establece qué tipo de archivos debe contener cada una. El objetivo es que todos los integrantes trabajemos con la misma organización, evitemos duplicar archivos y podamos integrar nuestros aportes sin interferir con el trabajo de los demás.

El proyecto se organiza alrededor de tres componentes principales:

- **Servidor en C++:** recibe solicitudes mediante XML-RPC, valida las operaciones solicitadas y coordina las acciones del sistema.
- **Cliente en Python:** permite que el usuario interactúe con el servidor desde una interfaz de línea de comandos. Esta interfaz podrá ampliarse posteriormente.
- **Firmware de Arduino:** controla el hardware del robot. Se utiliza el firmware proporcionado por la cátedra, conservándolo completo y sin modificaciones, salvo que la consigna o el equipo docente indiquen lo contrario.

También se contemplan carpetas para almacenar datos, registrar la actividad del sistema y documentar su funcionamiento.

## 2. Estructura general

La estructura de trabajo es la siguiente:

```text
TP_integrador_real/
├── server/
│   ├── xmlrpc/
│   ├── include/
│   ├── src/
│   └── Makefile
├── client/
├── firmware/
│   └── arduino/
├── data/
│   ├── db/
│   ├── logs/
│   └── trayectorias/
├── docs/
├── README.md
└── .gitignore
```

Esta estructura establece una separación entre los componentes del sistema. Los nombres de los archivos concretos podrán definirse a medida que avance la implementación, pero se debe mantener la separación de responsabilidades.

## 3. Servidor: `server/`

En esta carpeta se encuentra el código del servidor desarrollado en C++. Su responsabilidad es procesar las solicitudes recibidas, ejecutar la lógica correspondiente, comunicarse con el robot y devolver resultados al cliente.

### `server/xmlrpc/`

Contiene la biblioteca de XML-RPC en C++ utilizada para implementar la comunicación entre el cliente y el servidor. Los archivos de esta biblioteca provienen del trabajo anterior de XML-RPC.

Se debe conservar la estructura interna de la biblioteca y sus archivos relacionados. No conviene mezclar su implementación con las clases propias del trabajo integrador, ya que esto dificultaría distinguir el código de terceros del código desarrollado por el grupo.

### `server/include/`

Contiene los archivos de cabecera propios del servidor, generalmente archivos `.h` o `.hpp`.

Aquí se declaran las clases, sus atributos, sus métodos y las interfaces que necesitan conocer otros componentes del prog rama.

Por ejemplo, si se implementan clases como `Robot`, `Usuario`, `ControladorRobot` o `GestorUsuarios`, sus declaraciones podrán ubicarse en esta carpeta.

### `server/src/`

Contiene los archivos fuente `.cpp` correspondientes a las clases y funciones propias del servidor.

Aquí se implementará la lógica del sistema: la administración de usuarios, la validación de permisos, el procesamiento de las solicitudes XML-RPC, la coordinación del robot y la gestión de errores.

El archivo `main.cpp` del servidor también se ubicará aquí. Será el punto de entrada del programa y se encargará de inicializar los componentes necesarios y poner en funcionamiento el servidor.

### `server/Makefile`

Contiene las instrucciones de compilación del servidor y de los archivos C++ que necesita.

La compilación debe contemplar tanto el código propio como los archivos necesarios de la biblioteca XML-RPC. La estructura definitiva de las instrucciones de compilación se establecerá cuando se integre el código.

## 4. Cliente: `client/`

Contiene el código desarrollado en Python para que el usuario interactúe con el sistema y envíe solicitudes al servidor.

El cliente y el servidor son programas independientes: el cliente solicita operaciones y el servidor las procesa. No se debe implementar en el cliente la lógica que corresponde exclusivamente al servidor, como la validación definitiva de permisos o la ejecución de acciones sobre el robot.

Como organización inicial, se proponen los siguientes archivos:

- `main.py`: punto de entrada del cliente.
- `interfaz_cli.py`: administra la interacción con el usuario mediante la terminal, por ejemplo, mostrando opciones y leyendo comandos.
- `cliente_rpc.py`: reúne las funciones necesarias para conectarse al servidor mediante XML-RPC e invocar sus métodos.
- `modelos.py`: puede contener las clases o estructuras que el cliente necesite para representar solicitudes, respuestas u otros datos intercambiados.

Estos nombres son una propuesta inicial. Se podrán ajustar cuando se defina el diseño definitivo, manteniendo la separación entre interfaz de usuario, comunicación y representación de datos.

El cliente puede utilizar la biblioteca estándar de Python para XML-RPC, por lo que no es necesario instalar una biblioteca externa únicamente para realizar estas llamadas.

## 5. Firmware: `firmware/arduino/`

Contiene el firmware de Arduino proporcionado por la cátedra.

Se debe copiar o conservar **la carpeta completa del firmware original**, incluyendo el archivo `.ino` y todos los archivos adicionales que este incluya o necesite para compilar.

No se debe copiar solamente el archivo `.ino`, ya que podría depender de otros archivos. Tampoco se deben modificar arbitrariamente sus nombres, rutas relativas o instrucciones `#include`, porque podrían dejar de funcionar las dependencias del programa.

El firmware se compila y se carga en Arduino mediante las herramientas correspondientes. No forma parte de la compilación del servidor C++.

El servidor se comunicará con Arduino a través del puerto serie. La lógica de comunicación serie del lado del servidor pertenece al código propio de `server/`, mientras que el código que se ejecuta en el microcontrolador permanece en `firmware/arduino/`.

## 6. Datos del sistema: `data/`

Esta carpeta reúne los datos que el sistema necesita almacenar o genera durante su funcionamiento.

### `data/db/`

Destinada a los archivos relacionados con la persistencia de datos del sistema, por ejemplo, usuarios, configuraciones u otros registros persistentes, según el mecanismo de almacenamiento que finalmente se implemente.

### `data/logs/`

Destinada a los registros de actividad del servidor. Estos registros podrán incluir información como la fecha y hora de los eventos, el usuario que realizó una solicitud, la operación ejecutada y el resultado obtenido.

Los registros globales del servidor y los informes de actividad de los usuarios deberán generarse de acuerdo con los requisitos de la consigna.

### `data/trayectorias/`

Destinada a los archivos relacionados con las trayectorias del robot. Por ejemplo, podrá almacenar archivos G-Code que se carguen para su posterior consulta o ejecución.

La gestión de estos archivos debe realizarse mediante las funciones previstas en el sistema, evitando que el cliente pueda acceder arbitrariamente a rutas del servidor.

**Importante:** los archivos de datos que se generen durante la ejecución no necesariamente deben subirse a Git. Se deberá definir en `.gitignore` cuáles son datos locales o generados automáticamente y cuáles deben versionarse para compartir el proyecto.

## 7. Documentación: `docs/`

Contiene la documentación técnica del proyecto, separada del código fuente.

Se proponen los siguientes documentos:

- `arquitectura.md`: describe los componentes principales, sus responsabilidades y sus relaciones.
- `api_xmlrpc.md`: documenta los métodos que expone el servidor, sus parámetros, los resultados esperados y los posibles errores.
- `protocolo_serie.md`: reúne la información sobre la comunicación entre el servidor y Arduino, incluyendo los comandos y las respuestas que efectivamente admite el firmware.
- `pruebas.md`: registra las pruebas realizadas, los resultados obtenidos y los problemas detectados.

La documentación debe mantenerse actualizada a medida que cambie la implementación.

## 8. Archivos de la raíz

### `README.md`

Presenta el proyecto y explica cómo preparar el entorno, compilar el servidor, ejecutar el cliente y realizar las pruebas básicas. También puede indicar las dependencias necesarias y los requisitos de hardware.

### `.gitignore`

Define qué archivos y carpetas Git no debe incorporar al repositorio. Por ejemplo, ejecutables generados por la compilación, archivos temporales del editor, registros locales y otros datos que no sea necesario compartir.

No se deben ignorar archivos necesarios para compilar el programa ni dependencias que el equipo haya acordado versionar.

## 9. Criterios de trabajo en equipo

Para evitar conflictos durante el desarrollo, todos los integrantes deben respetar los siguientes criterios:

1. **Cada componente tiene una ubicación definida.** El código del servidor va en `server/`, el cliente en Python va en `client/` y el firmware original va en `firmware/arduino/`.

2. **Se debe evitar mezclar responsabilidades.** La interfaz presenta opciones al usuario; el cliente realiza las llamadas XML-RPC; el servidor valida y procesa las operaciones; y Arduino ejecuta el firmware de control proporcionado.

3. **Los cambios deben integrarse sin duplicar archivos.** Antes de crear una nueva clase, función o documento, se debe revisar si ya existe un componente con esa responsabilidad.

4. **Las interfaces deben acordarse entre los integrantes.** Cuando se agregue o modifique un método XML-RPC, se deben mantener coherentes su nombre, sus parámetros, su respuesta y su documentación para que los clientes puedan utilizarlo correctamente.

5. **Se debe preservar el trabajo previo.** La biblioteca XML-RPC y el firmware proporcionado deben conservar los archivos necesarios para su funcionamiento. Los cambios sobre estos componentes deben realizarse únicamente cuando sean necesarios y estén acordados.

6. **Git debe utilizarse para compartir cambios del proyecto, no archivos generados innecesarios.** Antes de confirmar cambios, hay que revisar qué archivos se están incorporando.

7. **La documentación y el código deben permanecer sincronizados.** Si cambia la interfaz de un método, la forma de ejecutar el sistema o el protocolo de comunicación, también debe actualizarse la documentación correspondiente.

## 10. Nota para el uso de asistentes de IA

Este documento sirve como contexto común para cualquier asistente de IA que ayude a un integrante del grupo.

Al proponer cambios, el asistente debe respetar esta estructura, evitar sobrescribir trabajo existente y consultar los archivos reales del repositorio antes de asumir que una clase, método o dependencia ya existe.

La organización presentada es una estructura inicial de trabajo. Los nombres definitivos de las clases, los métodos XML-RPC y los archivos podrán modificarse por acuerdo del grupo, pero cualquier cambio de organización deberá comunicarse y reflejarse en este documento.
